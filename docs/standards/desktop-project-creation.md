# Desktop project creation and agent handoff

**Status: implemented in source, not yet verified in a built application.** An
explicit desktop application choice now creates a real project scaffold and can
optionally hand a bounded desktop-specific brief to the already selected,
available local coding agent through the existing first-run run path. The
desktop target is intentionally exclusive and truthful: it creates a
Windows-only source scaffold with a Squirrel.Windows packaging target and
code signing disabled. No installer or release is created by this flow.

## Requirement

Choosing the desktop application target is a product intent, not a label added to
an otherwise ordinary web prototype. Project creation must materialize a
versioned scaffold with a real HTML entry point, package metadata, Electron main,
preload and renderer files. The generated shell keeps context isolation and
sandboxing enabled, disables Node integration and webviews, blocks network and
out-of-root local-file requests, denies secondary windows, and exposes only a
narrow typed preload marker. It must not expose arbitrary shell, filesystem,
environment, credential, or untyped IPC access.

The optional wire-up choice shows the app-wide selected local agent in a
searchable, keyboard-accessible picker. It never silently falls back to the
first available agent. The checkbox is off by default and is labelled `Wire up
after creation`; when enabled, the daemon re-reads the application config,
requires the requested id to match that witness, confirms the id exists in the
runtime registry, and confirms the same id is currently available. The bounded
brief is user data, not a trusted control string, and is passed as the one
authoritative `pendingPrompt` through the existing first-run path. The daemon
stores a `queued` wire-up receipt; the existing run status remains authoritative
for queued, running, completed, cancelled, and failed outcomes. This feature
does not create a second run or event protocol.

## Generated project state

The daemon owns `desktopScaffold` and `desktopWireup` metadata. Scaffold state is
versioned by `schemaVersion` and `revision`, records the source entry and renderer
bootstrap, and names every generated file role. Generated files are claimed in a
newly created, empty project directory before the database transaction. A
nonce-bearing `.desktop-scaffold-claim.json` marker records `staging`, `ready`,
and `published` states. Each generated byte is written through a unique
temporary file, read back, hashed, and checked against the complete nine-role
set before the project row and seed conversation become visible. A transaction
or publication failure removes only the exact directory whose ownership marker
matches the nonce; a pre-existing or concurrent directory is rejected and
preserved. Daemon startup reconciles stale owned claims: a claim with a
committed project is finalized, while an orphaned valid claim is removed.

The source starter is intentionally small and editable: `index.html`,
`styles.css`, and `app.js` provide a real local entry without user data, network
access, or a fake completed product. The companion `desktop/` folder contains
the package, main, preload, renderer, configuration, and README files needed for
the next implementation step. The versioned state enumerates all nine generated
roles. Package identity is derived from immutable `projectId`; `productName` is
the display label, so renaming a project does not move installed data or its
update identity. It is a source scaffold, not an installer.

## Export

The complete project ZIP export is project-scoped and does not depend on the
currently active file. It can prepare an empty project with only the generated
handoff/manifests, and it refuses
case-insensitive collisions with project-owned `desktop/` files, requires an HTML
entry, and records Squirrel.Windows as the eventual Windows packaging target with
code signing disabled. The export does not run a package manager, create an
installer, or publish anything.

The desktop scaffold remains a separately named target. The ordinary project
handoff never silently adds or substitutes the scaffold; both paths share the
same project-root source boundary and staged editor/download receipt.

## Failure and security boundaries

- An absolute, escaping, or non-HTML entry file is rejected before generation.
- Existing generated paths are rejected rather than overwritten.
- Desktop application selection is exclusive; responsive, mobile, tablet, and
  web-desktop targets cannot be silently retained alongside it.
- The generated main process canonicalizes the source root, HTML entry,
  renderer bootstrap, and every local file request immediately before use. It
  rejects lexical escapes, canonical escapes, symlink/reparse components, and
  non-regular files.
- The renderer receives no Node integration and no arbitrary IPC capability.
- Navigation and requests are limited to the exported source root and local
  `file:` content; network requests and secondary windows are denied.
- The selected agent is the existing application selection and is revalidated
  against the runtime registry, current availability, and the application
  configuration witness. No credentials, controls, or shell command text are
  accepted from project metadata.
- A wire-up prompt is bounded before it is persisted, must exactly match the
  shared prompt helper at the top-level `pendingPrompt` boundary, and is sent
  only through the existing first-run run machinery.

## Verification

Source-level coverage is present in:

- `design/apps/daemon/tests/desktop-scaffold.test.ts`
- `design/apps/daemon/tests/project-archive.test.ts`
- `design/packages/contracts/tests/system-prompt.test.ts`
- `design/packages/contracts/tests/scenario-defaults.test.ts`
- `design/apps/daemon/tests/prompts/system.test.ts`
- `design/apps/web/tests/components/NewProjectPanel.test.tsx`

The source contract also covers empty-directory claims, ownership markers,
project-stable package identity, exclusive target selection, selected-agent
validation, prompt parity, canonical path checks, and recoverable cleanup.

Those tests were not run locally because this repository's local lane does not
run Node, pnpm, Electron, builds, or test suites. The remaining proof is a hosted
source/test run plus a cheap-headless interaction that creates a desktop project,
inspects the generated file roles and metadata, exercises the optional wire-up,
and confirms the run state through the existing route.
